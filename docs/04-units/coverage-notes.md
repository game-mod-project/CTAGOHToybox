## 수기 메모

2026-10-11, 게임 버전 1.0.6.7 기준.

### 이 검증이 보장하는 것과 보장하지 않는 것

| 검사 | 잡아내는 것 | 잡아내지 못하는 것 |
|---|---|---|
| 1. 파일 | 상태가 붙지 않은 파일, 같은 경로에 내용이 다른 파일 | 추출기가 pak의 항목을 아예 보지 못한 경우 (1b가 맡는다) |
| 1b. pak 항목 수 | 색인의 행 수가 pak의 실제 파일 수와 다른 경우 | |
| 2. 왕복 | 괄호나 따옴표의 짝이 맞지 않는 파일 | 토크나이저가 글자를 버린 경우 (2b가 맡는다) |
| 2b. 글자 수 | 토크나이저가 글자를 버린 경우. 정규식과 별개의 방식으로 센 글자 수와 대조한다 | 글자는 다 읽었지만 뜻을 잘못 나눈 경우. 예: 이 문법에 없다고 가정한 주석 기호가 실제로는 주석인 경우 |
| 3. 키 | 스키마 문서가 데이터보다 낡았거나 손으로 고쳐진 경우 | 데이터 자체에 키가 빠진 경우 |

정리하면 "pak의 모든 파일을 보았고, 텍스트 파일의 모든 글자가 토큰이 되었고, 모든 토큰이 트리에 들어갔고, 트리의 모든 키가 문서에 있다"까지는 기계적으로 확인된다. 다음은 확인되지 않는다.

- **범위 판단이 옳은지.** 유닛 범위 밖으로 분류한 190,443개 파일(맵, 인터페이스, 건물·지형 엔티티 등) 안에 유닛에 영향을 주는 정의가 있을 가능성.
- **텍스트가 아닌 것으로 분류한 파일.** 확장자 목록과 앞부분의 NUL 바이트로 판정한다.
- **매크로 호출의 인자 값 자체.** `("crew_human" seat(2))`의 `seat(2)` 같은 인자는 그 매크로 호출 행의 값으로 실린다. 인자 안에 든 블록(`off({sensor})`)은 `.../off()/sensor`처럼 따로 키로도 나온다(바닐라에 22종).
- **문법 가정.** 블록 주석이 없다, 문자열 이스케이프가 없다는 가정은 왕복 검사로 증명되지 않는다. 별도로 확인한 것: 모델 파일을 뺀 바닐라 텍스트 17,928개에서 `\"`로 끝나는 문자열, 주석 밖의 `/*`, 여러 줄에 걸친 문자열이 없었다(코드 리뷰에서 독립적으로 훑은 결과).

### 왕복 검사에 실패한 파일

`set/multiplayer/units/early/units_eng.set` 하나다. 원본에 닫는 괄호가 네 군데 남는다. 예를 들어 `squad_rec_mc_early_all`을 정의하는 매크로 호출이 `t()))`로 끝난다. 파서 문제가 아니라 파일 자체의 오류다. 파서는 남는 괄호를 버리고 나머지를 읽으며, 이 파일은 키 목록과 카탈로그에 `ParseErrors` 표시와 함께 실려 있다. 게임이 이 파일을 어떻게 처리하는지는 확인하지 않았다.

### 펼치지 못한 구문

유닛 파일 16,230개 중 16개에 채워지지 않은 매개변수가 남는다. include 대상을 찾지 못했거나 정의가 없는 매크로는 없다.

| 매개변수 | 파일 수 | 예 |
|---|---|---|
| `%door2` | 11 | `eng/tank_light/stuart5_recce`, `ussr/tank_light/zis30`, `usa/car/willys_mb` |
| `%base` | 3 | `generic/car/universal`, `germany/car/kfz70`, `usa/car/cckw_fuel` |
| `%group` | 2 | `generic/train/tram_eu`, `tram_sov` |
| `%door3` | 1 | `eng/tank_light/vickers_aa_mk1` (`%door2`도 함께) |

매크로 본문이 `%door2`를 쓰는데 호출하는 쪽이 `door(...)`만 주는 식이다. 엔진이 채워지지 않은 매개변수를 빈 값으로 보는지, 문자 그대로 두는지는 확인하지 못했다. 이 문서의 데이터에는 `"%door2"`처럼 원문 그대로 남아 있다.

처음 실행에서는 27개 파일이 `properties/shadow/round.inc`와 `tank.inc`를 찾지 못했다. 두 파일은 pak 안에 0바이트로 들어 있었고 추출기가 빈 파일을 건너뛰어서 생긴 문제였다. 범위 안의 빈 파일도 추출하도록 고친 뒤 해소됐다.

### 추론한 규칙의 검증 결과

| 규칙 | 결과 |
|---|---|
| 가상 경로 = pak의 폴더 + pak 안의 경로 | 맞음. `/`로 시작하는 include가 전부 풀렸다 |
| 상대 include는 그 파일의 폴더 기준 | 맞음. `ability.inc`, 차량 폴더의 `.ext`가 전부 풀렸다 |
| 조상 폴더의 `.presets`는 암묵적으로 로드된다 | 맞는 것으로 보임. 아이템 2,720개에서 풀리지 않은 매크로가 0개 |
| 매크로 인자는 `이름(값)` → `%이름`, `args a b` → `%0 %1` | 대체로 맞는 것으로 보임. 채워지지 않은 매개변수가 16개 파일에 남는다(위 표) |
| 이름 있는 매개변수는 낱말 전체가 같아야 한다 | 추정. `%door`가 주어져도 `%door2`는 채우지 않는다. 위치 인자만 `"%0_left"`처럼 뒤에 글자가 붙을 수 있다고 보았다 |
| 매크로 안에서 부른 매크로는 바깥 매크로의 인자를 물려받는다 | 추정이지만 바닐라의 결과에는 영향이 없다. 물려받은 인자로 값이 채워진 유닛 파일이 16,230개 중 0개다 |
| 블록 주석 `/* */`와 문자열 이스케이프는 없다 | 맞는 것으로 보임. 위 "문법 가정" 참고 |

"맞는 것으로 보임"은 풀리지 않은 것이 없다는 뜻이지 엔진이 같은 순서와 범위로 처리한다는 증명이 아니다. 예를 들어 `.presets`가 하위 폴더에까지 적용되는지, 같은 이름의 매크로가 여러 번 정의되면 어느 쪽이 쓰이는지는 구분해 확인하지 못했다. 이 구현은 나중 정의가 이긴다.

산술식을 계산한 값은 소수 15자리까지 적는다.
### 같은 가상 경로의 충돌

유닛 범위 안에서 같은 가상 경로를 가진 파일은 없었다(`duplicate` 0, `collision` 0).

### 키 경로를 묶은 규칙

이름이 따옴표 문자열인 블록은 경로에서 `"*"`로 묶고 이름을 값에 남겼다. 묶지 않으면 공용 그룹의 키가 60,332개가 되는데 대부분 유닛 이름이나 텍스처 경로 같은 데이터다. 묶은 뒤 11,281개다. 이름은 `units-*.jsonl.gz`의 값에 그대로 있으므로 잃은 정보는 없다.

### 의미를 살펴본 범위

사람이 등급을 매긴 것은 `data/annotations/common.psv`의 항목이다. 펼친 뒤의 키 가운데 유닛 종류별로 파일의 5% 이상에 나오는 434개를 모두 포함한다. 아이템에서 동작 설정 파일 7개(`.fsm`, `.hand`, `_settings` 폴더)를 뺀 뒤에도 434개가 모두 남아 있다. `*/이름` 형식의 주석은 유닛 파일과 펼친 키에만 적용했다. 공용 설정이나 모델 파일에는 같은 이름이 다른 뜻으로 쓰일 수 있어서다.

"확인" 등급의 근거는 게임 파일에 개발자가 남긴 주석이다. 주석이 오래되어 현재 동작과 다를 가능성은 배제하지 못한다.
