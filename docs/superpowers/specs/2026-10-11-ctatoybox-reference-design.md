# CTAToybox 레퍼런스 구축 설계

- 작성일: 2026-10-11
- 대상 게임: Call to Arms - Gates of Hell: Ostfront (Steam appid `400750`, buildid `25492057`, 실행 파일 버전 `1.0.6.7`)
- 게임 경로: `E:\SteamLibrary\steamapps\common\Call to Arms - Gates of Hell`
- 저장소 경로: `E:\CTAToybox`

## 1. 목적

특정 모드를 정하지 않은 상태에서, 이후 어떤 모드든 만들 수 있도록 범용 참조 자료를 구축한다.

### 사용자가 요청한 것

1. 게임 구조 확인
2. 모드 개발 구성 리서치 (웹, 스팀 창작마당, 모드 사이트 모두 확인)
3. 모드 폴더 설정
4. 인게임 모든 유닛의 상태 구성 분석 (게임 폴더의 유닛 정보 파일을 분석하고, 유닛을 구성하는 정보를 하나도 누락 없이 정리)
5. 4번에 더해 스팀 창작마당 모드에서 추가된 구성 확인

3번을 제외한 나머지는 문서만 구성하고 모드 코드 작업은 하지 않는다.

### 대화에서 합의한 것

- 최종 모드 종류는 미정이며 범용 레퍼런스를 만든다.
- 5번의 대상은 프로필 `options.set`에 등록된 4개 모드다: `2905667604`(MACE), `3732639687`(Fusion ENG), `3295913567`(Spawn Menu), `2829744930`(Auto Medic/AA/Weather). 모드 이름은 7월 작업 문서에 적힌 것이며 파일 확보 후 `mod.info`로 확정한다.
- 분석 스크립트는 허용하며 `tools\`에 보관한다. 모드 코드가 아니라 문서 생성·검증 도구다.
- 접근 방식은 "스키마 전수 + 생성 카탈로그"다.
- steamcmd 다운로드와 실행을 허락받았다.

### 가정

- "유닛"은 조작·스폰 가능한 모든 대상(보병, 차량, 화포, 항공기)과 그것이 참조하는 구성 요소(무기, 탄약, 장갑, 인벤토리, 상속 속성, 편제·비용, 표시 이름)를 포함한다.
- 문서는 한국어로 쓰고 키·식별자·파일명은 원문 그대로 둔다.

### 성공 기준

- 5.2절의 세 가지 검사가 모두 미해결 0건이거나, 통과하지 못한 항목이 `coverage.md`에 목록으로 남아 있다.
- 1~5번 각각에 해당하는 문서가 `docs\`에 있다.
- 게임의 모드 목록에 `CTAToybox`가 표시된다(게임 실행 확인은 사용자가 한다).

## 4. 모드 폴더 설정 (요청 3번)

- 게임은 `게임폴더\mods\<이름>`만 로컬 모드로 인식하며 폴더명은 `[a-zA-Z_]+`를 따라야 한다(공식 템플릿 `readme.txt`).
- 모드 본체는 `E:\CTAToybox\mod\CTAToybox`에 둔다.
- `게임폴더\mods\CTAToybox`를 위 경로로 향하는 디렉터리 정션으로 만든다.
- `mod.info`는 `name`을 폴더명과 같게, `desc`, `minGameVersion`, `maxGameVersion`을 채운다. 버전 표기 형식은 템플릿 readme의 규칙과 현재 실행 파일 버전 1.0.6.7을 대조해 정하고, 근거를 `03-mod-folder-setup.md`에 적는다.
- `resource\`와 `localizations\`는 빈 뼈대다. 게임 동작을 바꾸는 파일은 넣지 않는다.
- 게임 폴더의 기존 모드와 파일은 건드리지 않는다.

## 5. 유닛 분석 (요청 4번)

### 5.1 파이프라인

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 1. 추출 | 모든 pak에서 텍스트 정의 파일만 꺼낸다. 바이너리는 경로·크기만 기록한다 | `_work\vanilla\`, `data\file-index.csv` |
| 2. 파싱 | 블록 문법(`{키 값 ...}`, `;` 주석, `(include ...)`, `(define ...)`, 매크로 호출, 따옴표 문자열)을 트리로 바꾼다 | 메모리 내 트리 |
| 3. 키 집계 | 블록 경로 단위로 모든 키를 수집한다: 등장 파일 유형, 횟수, 값 형태, 값 범위, 예시 파일 | `data\keys-<유형>.csv` |
| 4. 유닛 카탈로그 | 유닛마다 모든 키·값을 기록한다. 적힌 그대로의 값(raw)과 include·매크로를 펼친 값(resolved)을 구분한다 | `data\units-<유형>.json` |
| 5. 참조 연결 | 유닛에서 무기, 탄약, 인벤토리, 상속 속성, 표시 이름, 편제·비용으로 이어지는 참조를 기록한다 | `data\references.csv` |
| 6. 검증 | 5.2절의 검사를 실행한다 | `docs\04-units\coverage.md` |

파일 확장자와 문법은 추출 후 실제 파일로 확정한다. 2절의 표에 없는 유형이 유닛 정의에 관여하는 것으로 드러나면 대상에 추가한다.

resolved 값은 스크립트가 재현할 수 있는 범위(include, define, 매크로)까지만 계산한다. 재현하지 못한 구문은 raw로 남기고 `coverage.md`에 목록으로 적는다.

### 5.2 누락 검증

1. **파일 검사**: pak의 모든 파일이 "파싱됨" 또는 "제외됨(사유 명시)" 중 하나에 속한다. 어디에도 속하지 않는 파일이 0개여야 한다.
2. **왕복 검사**: 파싱한 트리를 텍스트로 다시 써서 원본과 비교한다(공백·주석 제외). 다른 파일은 실패로 기록한다.
3. **키 검사**: `keys-*.csv`의 모든 키가 `schema-*.md`에 행으로 존재한다. 스크립트가 대조하고 빠진 키 수를 출력한다.

실패 항목은 숨기지 않고 `coverage.md`에 남긴다.

### 5.3 키 의미의 근거 등급

| 등급 | 기준 |
|---|---|
| 확인 | 공식 문서나 위키에 설명이 있다. 출처 URL을 적는다 |
| 추정 | 이름, 값 분포, 사용 맥락에서 추론했다. 근거를 적는다 |
| 미확인 | 의미를 알 수 없다. 값 범위와 예시만 싣는다 |

의미를 알 수 없는 키도 빼지 않는다. 엔진 실행 파일 내부 동작은 분석하지 않는다.

### 5.4 범위

- 포함: 유닛을 정의하는 모든 텍스트 파일, 표시 이름(`localizations`), 편제·비용. 봇 구매 관련 Lua는 참조 목록으로 싣는다.
- 제외: 메시·애니메이션·텍스처·사운드의 내부 내용(유닛이 참조하는 파일 경로는 기록한다), 맵·미션 파일.

## 8. 창작마당 모드 분석 (요청 5번)

1. steamcmd를 `_work\steamcmd\`에 내려받아(Valve 공식 배포본) 4개 모드 다운로드를 시도한다. 거부되면 사용자에게 Steam 재구독을 요청하고 이후 작업을 이어받는다.
2. 모드마다 5.1절의 파이프라인을 실행한다.
3. 바닐라와 비교한다: 새 유닛, 새 키, 덮어쓴 파일, 값이 바뀐 기존 유닛.
4. 모드 간 충돌(같은 파일을 여러 모드가 덮어씀)과 각 모드의 `mod.info` 지원 버전을 현재 버전 1.0.6.7과 함께 기록한다.

산출물은 `docs\05-workshop-mods\`의 모드별 문서와 `data\mods\<id>\`의 생성 데이터다. 모드 원본 파일은 `_work\`에만 둔다.
