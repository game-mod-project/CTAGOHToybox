# 스탯 편집기 설계 (하위 프로젝트 A)

작성: 2026-10-12. 기준: 게임 1.0.6.7.

## 배경과 전체 그림

요청은 네 가지였다.

1. 바닐라와 모드의 모든 유닛(보병, 전차, 무기, 포탄 등)의 모든 스탯을 고치는 외부 실행 파일
2. 기존 Spawn Menu를 대체하는 모드 구조. 바닐라와 모드의 모든 유닛을 캠페인·컨퀘스트·스커미시 안에서 소환
3. 컨퀘스트·스커미시 설정의 상세 변경. 1의 실행 파일에 포함
4. 그 외 추가 기능 검토

한 스펙으로 묶기에는 커서 셋으로 나눴다. 이 문서는 A만 다룬다.

| | 하위 프로젝트 | 상태 |
|---|---|---|
| A | 편집기 코어와 스탯 편집 | 이 문서 |
| B | 컨퀘스트·스커미시 설정 편집. A의 코어 위에 얹는다 | 설정 파일 조사 뒤 별도 스펙 |
| C | 스폰 모드 | Spawn Menu의 동작 방식 조사(spike) 뒤 별도 스펙 |

4번은 A~C의 윤곽이 잡힌 뒤에 검토한다.

## 합의한 전제

| 항목 | 결정 |
|---|---|
| 사용자 | 본인만, 싱글플레이. 배포·동기화·자산 허락은 범위 밖 |
| 편집 단위 | 유닛 하나씩. 일괄 규칙은 없다 |
| 화면 | 뜻을 아는 키만 모은 요약 화면과, 모든 키를 보여 주는 전체 트리 |
| 공유되는 값 | 고칠 때마다 "전부 / 이 유닛만"을 고른다 |
| 형태 | Windows 데스크톱 앱. WPF, .NET 8, 외부 패키지 없음 |
| 수정의 보관 | 수정 목록을 프로젝트 파일에 저장하고, 빌드로 모드 폴더를 다시 만든다 |
| 게임 폴더 | 읽기만 한다. 출력은 `mod/CTAToybox/resource`에만 쓴다 |
| "모드 유닛" | 프로필의 `options.set`에 켜져 있는 모드의 유닛 |

## 구성

```
editor/
├─ CtaToybox.Core/        UI 없는 라이브러리 (net8.0)
│   ├─ Sdl/               파서와 리졸버. tools/lib/*.cs를 옮겨 온다
│   ├─ Sources/           원본 계층: 바닐라 pak + 켜 둔 모드, 로드 순서대로
│   ├─ Units/             유닛 목록과 유닛을 이루는 파일 묶음
│   ├─ Provenance/        펼친 값 → 원본 파일과 토큰 위치, 공유하는 유닛 목록
│   ├─ Edits/             수정 목록(프로젝트 파일) 읽기·쓰기·검증
│   └─ Build/             수정 적용 → mod/CTAToybox/resource 생성
├─ CtaToybox.Core.Tests/  코어 테스트
└─ CtaToybox.App/         WPF 화면 (net8.0-windows). 코어만 호출한다
```

| 부분 | 하는 일 | 의존 |
|---|---|---|
| Sources | 가상 경로를 주면 지금 게임이 읽을 파일의 내용을 돌려준다. pak은 ZIP으로 직접 읽는다 | 게임 폴더, `options.set` (읽기 전용) |
| Units | 유닛 검색. 유닛 하나의 파일 묶음(본체, include한 파일, 참조하는 무기와 탄약) | Sources, Sdl |
| Provenance | 펼친 트리의 각 값이 어느 파일 몇 번째 글자에서 왔는지, 그 자리를 쓰는 다른 유닛이 누구인지 | Sdl |
| Edits | 수정 한 건의 저장 형식. 원본이 바뀌었는지 검사 | 없음 |
| Build | 수정 목록을 원본에 적용해 출력 폴더를 다시 쓴다 | Sources, Edits |

### 기존 코드와의 관계

- `tools/lib/*.cs`(파서, 리졸버, 집계)를 코어로 옮긴다. PowerShell 스크립트는 빌드된 DLL을 불러 쓴다. 같은 파서를 두 벌 두지 않는다.
- 토큰에는 원본 텍스트 안의 위치(`SdlToken.Index`)가 이미 있다. 값 토큰만 바꿔 쓰는 데 이것을 쓴다.
- 리졸버는 펼친 노드가 어느 파일에서 왔는지 기억하지 않는다. 출처 추적을 추가한다: 노드마다 (가상 경로, 토큰 위치, 어떤 include·매크로를 거쳤는지)를 붙인다.
- 편집기는 `_work/`나 `data/`의 추출본이 아니라 게임 폴더의 pak을 직접 읽는다. `data/`에서 쓰는 것은 키 설명(`data/annotations/common.psv`)과 표시 이름(`data/display-names.csv`)뿐이다.

## 수정 한 건의 형태

프로젝트 파일은 `editor/projects/<이름>.json`이고 git으로 관리한다.

| 필드 | 내용 | 예 |
|---|---|---|
| `unit` | 어느 유닛을 열어 놓고 고쳤는지 | `entity/-vehicle/ger/tank_heavy/tiger1e/tiger1e.def` |
| `file` | 값이 실제로 있는 파일의 가상 경로 | `properties/tank_heavy.ext` |
| `path` | 그 파일 안에서의 키 경로와 같은 경로 중 몇 번째인지 | `/props/armor/front`, 0 |
| `arg` | 그 키의 몇 번째 인자인지 | 0 |
| `old` | 수정 당시의 원래 값 | `100` |
| `new` | 새 값 | `120` |
| `scope` | `shared`(전부) 또는 `unit`(이 유닛만) | `unit` |
| `enabled` | 끄고 켜기 | `true` |

`old`는 업데이트 감지에 쓴다. 빌드할 때 원본의 현재 값이 `old`와 다르면 그 수정은 적용하지 않고 "원본이 바뀜"으로 표시한다.

## 적용 범위별 동작

| 경우 | 동작 |
|---|---|
| `shared` | `file`을 출력 폴더의 같은 경로에 복사하고 해당 값 토큰만 바꾼다. 그 파일을 쓰는 모든 유닛이 바뀐다 |
| `unit`, include로 공유된 값 | 공유 파일은 건드리지 않는다. 그 파일의 사본을 유닛 전용 이름으로 만들어 값을 바꾸고, 유닛 본체의 `(include ...)`가 사본을 가리키게 고친다. include가 여러 단계면 유닛에서 그 값까지의 사슬만 사본으로 만든다 |
| `unit`, 매크로 인자로 주어진 값 | 유닛 파일의 매크로 호출에 있는 인자 토큰을 바꾼다 |
| `unit`, 매크로 본문 안에 고정된 값 | 첫 버전에서는 지원하지 않는다. `shared`만 고를 수 있고 이유를 표시한다 |
| 별도 파일 참조(무기, 탄약) | 첫 버전에서는 `shared`만 지원한다. 영향받는 유닛 목록을 보여 준다 |

## 빌드

1. 이전 빌드가 만든 파일을 지운다. 지울 대상은 `mod/CTAToybox/.ctatoybox-build.json`에 적힌 것뿐이다. 손으로 넣은 파일은 건드리지 않는다.
2. 켜진 수정을 `file`별로 묶어, 원본을 읽고 `old`를 검사한 뒤 토큰을 바꾼다. 한 파일에 여러 건이면 뒤 위치부터 적용한다.
3. 쓴 내용을 다시 파싱해 왕복 검사를 한다. 실패한 파일은 쓰지 않고 오류로 보고한다.
4. 임시 폴더에 모두 쓴 뒤 출력 폴더로 옮긴다. 도중에 실패하면 이전 빌드 결과가 남는다.
5. 결과를 요약한다: 적용 N건, 원본이 바뀌어 건너뜀 N건, 대상 없음 N건, 오류 N건.

출력은 pak으로 묶지 않은 낱개 파일이다.

## 화면

창 하나, 세 칸.

```
┌──────────────────────────────────────────────────────────────────────┐
│ 프로젝트: my-tweaks   원본: 바닐라 + MACE + Fusion   [빌드]  수정 12건 │
├───────────────┬──────────────────────────────────┬───────────────────┤
│ 유닛 찾기     │ Tiger I E            [요약|전체] │ 수정 목록         │
│ [검색어____]  │                                  │                   │
│ 종류 [차량 ▾] │ 요약                             │ ☑ Tiger I E       │
│ 출처 [전체 ▾] │  전면 장갑   [100] → 120  ●      │   전면 장갑       │
│               │  최고 속도   [ 38]               │   100 → 120 유닛  │
│ ▸ 독일        │  ...                             │ ☑ 88mm APCBC      │
│   ▸ 중전차    │                                  │   관통 150 → 165  │
│     Tiger I E │ 전체                             │   전부(유닛 14개) │
│     Tiger II  │  ▾ tiger1e.def                   │ ⚠ T-34/76         │
│ ▸ 소련        │    ▾ props                       │   원본이 바뀜     │
│ ▸ MACE: 일본  │      armor front 100  공유 23 ⓘ  │                   │
│               │  ▾ 무기: 88mm KwK 36             │                   │
│               │  ▾ 포탄: 88mm APCBC              │                   │
└───────────────┴──────────────────────────────────┴───────────────────┘
```

(그림의 유닛 이름, 키 이름, 수치는 배치를 보이기 위한 예시다.)

- **유닛 찾기**: 표시 이름과 파일 경로로 검색한다. 종류와 출처(바닐라, 모드별)로 거른다. 수정이 걸린 유닛에 표시가 붙는다.
- **요약 탭**: 뜻을 아는 키만 이름을 붙여 보여 준다. 어떤 키를 올릴지는 `editor/summary/<종류>.psv`로 정한다. 첫 버전은 `data/annotations/common.psv`에서 등급이 "확인"인 키로 시작한다. 후보 목록은 `docs/06-editable-attributes/`의 "뜻을 아는 속성"이다.
- **전체 탭**: 유닛 본체, include한 파일, 참조하는 무기와 탄약을 차례로 트리로 보여 준다. 값마다 출처 파일과 공유 수를 표시하고, 설명이 있는 키에는 설명을 붙인다.
- **값 수정**: 공유되지 않는 값은 바로 수정 목록에 들어간다. 공유되는 값은 영향받는 유닛 목록과 함께 "전부 / 이 유닛만"을 묻는다. "이 유닛만"이 불가능한 자리는 선택지를 끄고 이유를 적는다.
- **입력 검사**: 형태만 본다. 숫자였던 자리에 숫자가 아닌 값을 넣으면 경고하되 막지 않는다. 값의 범위는 검사하지 않는다.
- **수정 목록**: 유닛별로 묶고, 건별로 끄기·되돌리기·삭제를 한다. "원본이 바뀜" 항목은 현재 원본 값을 보여 주고 유지할지 지울지 고르게 한다.
- **프로젝트 줄**: 원본 구성과 로드 순서를 보여 준다. CTAToybox가 수정 대상 모드보다 앞에 로드되면 경고한다. `options.set`은 고치지 않는다.

## 오류 처리

| 상황 | 동작 |
|---|---|
| 게임 폴더나 프로필을 찾지 못함 | 시작 화면에서 경로를 지정한다. `editor/settings.json`(git 제외)에 저장한다 |
| 원본 파일이 파싱되지 않음 | 읽기 전용으로 보여 주고 편집을 막는다 |
| 펼치기에서 풀리지 않은 구문 | 해당 값에 표시를 붙이고 편집은 허용한다 |
| 수정의 `old`가 원본과 다름 | 빌드에서 건너뛰고 "원본이 바뀜"으로 표시한다 |
| 수정이 가리키는 파일이나 키가 없어짐 | 빌드에서 건너뛰고 "대상 없음"으로 표시한다. 수정은 지우지 않는다 |
| 쓴 파일이 왕복 검사에 실패 | 그 파일을 쓰지 않고 오류로 보고한다. 나머지는 계속 빌드한다 |
| 게임이 실행 중 | 빌드 전에 경고한다. 막지 않는다 |

## 테스트

코어에 집중한다. 화면은 얇게 유지하고 자동 테스트에서 뺀다.

- **단위 테스트** (작은 가짜 파일):
  - 토큰 치환이 주석과 서식을 보존한다. 한 파일에 여러 건을 적용해도 위치가 밀리지 않는다
  - 출처 추적: include, 매크로 인자, 매크로 본문, `.presets` 각각에서 값의 원본 위치를 찾는다
  - "이 유닛만": include 사슬의 사본 생성과 include 경로 고쳐 쓰기
  - 원본 계층: 뒤에 로드된 모드의 파일이 이긴다
  - 수정 목록: `old` 불일치, 대상 없음, 끄기
- **실제 파일 검증** (게임이 설치된 PC에서만 도는 별도 묶음):
  - 바닐라의 모든 유닛 파일에 값을 같은 값으로 바꾸는 수정을 적용한 결과가 원본과 바이트 단위로 같다
  - 종류별 대표 유닛에 수정을 걸어 빌드한 결과가 왕복 검사를 통과한다
- **게임 안 확인** (수동, 체크리스트로 문서화): `shared`, include 사본, 매크로 인자를 각각 한 건씩 빌드해 게임에서 값이 바뀌었는지 본다.
- 기존 PowerShell 테스트(`tools/tests`)는 C# 코드를 옮긴 뒤에도 그대로 통과해야 한다.

## 구현 순서

1. **코어 이전**: `tools/lib/*.cs`를 코어 프로젝트로 옮기고 기존 테스트 통과를 확인한다.
2. **원본 계층, 토큰 치환, 빌드**: 화면 없이 명령줄로 수정 한 건을 빌드해 게임에서 확인한다.
3. **출처 추적과 "이 유닛만"**: 다시 게임에서 확인한다.
4. **화면**: 전체 탭, 수정 목록, 요약 탭 순서.

2단계에서 게임이 수정을 받아들이지 않으면 화면을 만들기 전에 설계를 고친다.

## 범위

**넣는 것**

- 유닛 검색과 열기, 요약 탭과 전체 탭
- 값 수정: `shared`, include 사본, 매크로 인자
- 수정 목록의 저장·끄기·되돌리기, 빌드, 업데이트 감지
- 로드 순서 경고

**빼는 것**

- 일괄 규칙
- 매크로 본문 안의 값을 "이 유닛만" 고치기
- 무기·탄약 복제
- 키나 블록의 추가·삭제. 있는 값을 바꾸는 것만 한다
- 새 유닛 만들기
- 모델 파일(`.mdl` 등), 맵·미션 파일, Lua 스크립트
- `options.set` 자동 수정

## 알려진 한계와 위험

- **펼치기 규칙은 추론이다.** 편집기가 "이 값이 이 유닛에 적용된다"고 보여 주는 것이 엔진의 실제 동작과 다를 수 있다. `(mod ...)`와 `{from "pattern ..."}`은 펼치지 않는다. 구현 순서 2·3단계의 게임 안 확인이 이 위험을 가장 먼저 드러낸다.
- **같은 경로의 파일은 나중에 로드된 쪽이 이긴다는 것도 추정이다**(`docs/02-modding-research.md`). `shared` 수정은 이 전제에 기댄다.
- **모드 안에서 낱개 파일과 pak이 겹칠 때의 우선순위는 미확인이다.** 원본 계층은 낱개 파일이 이긴다고 가정하고, 그런 겹침이 있는 파일을 열면 표시한다.
- **편집기는 문법이 깨지지 않는 것까지만 보장한다.** 값이 게임에서 의도대로 동작하는지는 보장하지 않는다.
- **include 사본의 이름 규칙**은 구현 순서 3단계에서 게임이 받아들이는 형태를 확인한 뒤 정한다. 폴더명 규칙(`[a-zA-Z_]+`)이 파일명에도 적용되는지 모른다.
