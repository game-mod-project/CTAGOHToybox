# F1: 일괄 규칙 설계

2026-10-17. 백로그 P2 추가 기능 검토의 1순위(`docs/11-feature-review.md` F1). 사용자 요청: "F1 일괄 규칙부터 설계해", "네 추천 방향으로 설계부터 진행". 사용자가 질문을 건너뛰었으므로 아래 결정은 표시한 것 말고는 모두 AI 판단이다. **상태: 구현 끝(2026-10-17).** 결과는 맨 아래 "구현 결과".

## 왜

지금 편집기는 유닛 하나를 열고 값 하나씩 고친다. 월드워 차종 작업(E18)에서는 경·중형전차 450대에 같은 수정을 넣으려고 프리셋 코드(`vision-preset --classes`)를 따로 썼다. 속도·장갑·탄약 수처럼 "이 종류의 유닛 모두에서 이 값을 이렇게"는 앞으로도 되풀이된다. 이것을 앱과 명령줄에서 고를 수 있게 한다.

## 목표

- 사용자가 **대상**(어떤 유닛들) × **키**(펼친 키) × **연산**(새 값·배수·더하기)을 고르면, 편집기가 대상 유닛마다 그 키의 원본 자리를 찾아 수정 목록을 만든다.
- 넣기 전에 **미리 보기**를 보인다: 바뀌는 유닛 수, 원래 값 → 새 값, 건너뛴 유닛과 이유, 대상 밖에 같이 바뀌는 유닛.
- 만든 수정은 지금의 수정과 같다. 점검·빌드·출력은 바꾸지 않는다. 규칙은 프로젝트에 남아 나중에 다시 적용하거나 통째로 끄고 지울 수 있다.

## 하지 않는 것

- 조건식, 다른 키를 참조하는 식(예: "장갑 = 무게 × 0.1"), 단계 함수.
- 키·블록 추가(없는 키를 새로 넣기). 대상 유닛에 그 키가 없으면 건너뛴다.
- 게임 안 확인(사용자 2026-10-16).
- 유닛 화면 밖의 파일(게임 설정)은 첫 판에서 대상에 넣지 않는다. 게임 설정은 파일 하나가 곧 항목이라 지금 화면으로 충분하다.

## 규칙의 모양

| 칸 | 뜻 | 예 |
|---|---|---|
| 대상 종류 | 편집기 종류(`tank`, `cannon`, `car`, `vehicle-other`, `breed`, `stuff`) | `tank` |
| 경로 거르기 | 유닛 가상 경로에 든 글자. 여럿이면 모두 들어야 한다. 없으면 그 종류 전부 | `/tank_light/` |
| 계층 | `바닐라` 또는 모드 하나. 없으면 전부(편집기 목록의 "출처"와 같다) | |
| 키 | 펼친 키 경로. 주석·요약과 같은 규칙으로 맞춘다(정확한 경로, `**/꼬리`, `KeyPattern.Candidates`의 `*/이름` 없이). 줄에 값이 여럿이면 몇 번째 값인지. 주지 않으면 첫 값(0). `모든 값`을 고르면 그 줄의 수인 값 모두(AI 판단) | `**/locomotion/maxspeed` 값 0 |
| 연산 | `set`(새 값), `mul`(배수), `add`(더하기) | `mul 1.1` |
| 범위 | `auto`(기본), `shared`, `unit` | `auto` |

- **연산 규칙**:
  - `mul`·`add`는 원래 값이 수일 때만 된다. 수가 아니면 건너뛴다.
  - 원래 값이 정수면 결과를 반올림해 정수로 쓴다. 소수면 소수 셋째 자리까지 쓴다. 정수→소수가 필요하면 `set`을 쓴다.
  - `set`은 새 값 검사(`ValueRules.CheckNewValue`)를 그대로 쓴다.
  - 결과가 원래 값과 같으면 수정을 만들지 않는다.
- **한 줄이 여러 번 펼쳐지는 키**(같은 키가 부위마다, 예: 장갑 볼륨): 규칙은 그 키의 모든 펼친 줄을 대상으로 한다. 사용자가 부위로 좁히려면 키를 정확한 경로로 쓴다.

## 원본 자리와 범위

- 대상 유닛마다 펼친 줄 가운데 키가 맞는 줄의 값 자리(`TraceValue`: 파일·키 경로·몇 번째·몇 번째 값)를 모은다. 계산·치환으로 만든 값, 꺼진 블록 등 고칠 수 없는 값은 건너뛰고 이유를 적는다.
- 같은 자리를 여러 대상 유닛이 같이 쓰면 하나로 모은다.
- **범위 `auto`**:
  - 그 자리의 파일을 쓰는 유닛(`UnitIndex.UsersOf`)이 모두 대상이면 '전부' 수정 하나를 만든다.
  - 대상 밖 유닛도 쓰면 대상 유닛마다 '이 유닛만' 수정을 만든다(`UnitScope.Blocker`가 막으면 건너뛴다).
- 범위 `shared`는 늘 '전부'다. 미리 보기에 "대상 밖 유닛 N개도 바뀐다"를 크게 보인다.
- 범위 `unit`은 늘 '이 유닛만'이다.
- **원형 상속(E14)**: 물려받은 값은 `UnitScope`의 규칙을 그대로 쓴다.

## 다른 수정과 겹칠 때 (AI 판단, 검토 뒤 정함)

- **같은 자리**는 원본 자리(파일·키 경로·몇 번째·몇 번째 값)가 같은 것이다. 범위('전부'·'이 유닛만')와 상관없다.
- **사람이 만든 수정**(규칙이 만들지 않은 것)이 이긴다.
  - 사람의 '전부' 수정이 그 자리에 있으면 규칙은 그 자리를 통째로 건너뛴다(모든 대상 유닛). 그대로 만들면 규칙 값이 원래 값에서 계산돼 사람 값을 덮기 때문이다.
  - 사람의 '이 유닛만' 수정이 유닛 U에 있으면 규칙은 U만 건너뛴다. 규칙이 그 자리에 '전부' 수정을 만들어도 빌드는 U에서 U의 '이 유닛만' 값을 쓴다(지금 빌드 규칙). 미리 보기에 U를 "직접 고친 수정이 있다"로 적는다.
- **규칙끼리**는 프로젝트의 `rules` 목록 순서가 이긴다(앞 규칙이 먼저). 뒤 규칙은 앞의 켜진 규칙이 가진 자리를 위와 같은 꼴로 건너뛴다. 쌓아 곱하지 않는다. 꺼진 규칙은 자리를 갖지 않는다.
- 그래서 규칙을 켜고 끄거나, 고치거나, 다시 적용하면 그 규칙과 **목록에서 뒤에 있는 규칙들을 차례로 다시 적용**한다.

## 프로젝트에 남기기

- 프로젝트 파일에 `rules` 목록을 더한다. 규칙마다 `id`(짧은 문자열), 이름(사용자가 붙임, 없으면 자동), 위 칸들, 켜짐을 적는다.
- 규칙이 만든 수정은 `Edit.Rule = <id>`를 단다. 사람이 고친 수정은 `Rule`이 없다. 지금 프로젝트 파일은 그대로 열린다.
- **다시 적용**: 원본이 바뀌었거나(모드 갱신) 규칙을 고쳤을 때, 그 규칙의 수정을 지우고 지금 원본으로 다시 만든다. 사람이 고친 수정은 건드리지 않는다.
- 규칙을 끄면 그 규칙의 수정이 모두 꺼진다. 규칙을 지우면 그 규칙의 수정이 모두 지워진다.
- 규칙이 만든 수정 하나를 사람이 고치거나 끄면 그 수정은 규칙에서 떨어진다(`Rule`을 지운다). 다시 적용해도 사람의 결정이 남는다.

## 화면 (앱)

- 전체·요약 탭의 줄을 오른쪽 단추로 눌러 **"이 키로 일괄 규칙..."**: 지금 유닛의 종류, 그 줄의 키, 그 값의 자리로 채운 규칙 창을 연다.
- 규칙 창: 위 칸들, "미리 보기" 단추, 미리 보기 목록(유닛 이름 · 원래 → 새 값 · 범위), 건너뛴 목록(유닛 · 이유), 합계, "수정 목록에 넣기".
- 수정 목록: 규칙이 만든 수정은 규칙 이름의 묶음으로 접어 보인다(묶음 머리에 켜고 끄기, 다시 적용, 지우기). 사람이 고친 수정은 지금처럼 유닛별 묶음이다.
- 미리 보기가 수천 건이면 목록은 앞의 500건만 보이고 합계는 모두 센다.

## 명령줄

- `rule preview --kind tank --path /tank_light/ --key "**/locomotion/maxspeed" [--arg 0] --mul 1.1 [--layer <계층>] [--scope auto|shared|unit]`: 미리 보기만 찍는다.
- `rule add --project <파일> --name "경전차 속도 10%" …같은 옵션…`: 규칙과 수정을 프로젝트에 넣는다.
- `rule list --project <파일>`, `rule edit --project <파일> --id <id> …`, `rule reapply --project <파일> --id <id>`, `rule remove --project <파일> --id <id>`, `rule enable|disable --project <파일> --id <id>`.

## 확인 방법 (게임 밖)

- 단위 테스트: 연산과 반올림, 정수·소수, 수가 아닌 값, 범위 `auto`의 두 갈래, '이 유닛만' 막힘, 사람 수정·다른 규칙과 겹침, 다시 적용, 끄기·지우기, 사람이 고친 규칙 수정이 떨어지는지, 예전 프로젝트 파일이 열리는지.
- 실제 파일 검사(`-- real`): 실제 판에서 "모든 탱크의 최고 속도 ×1.1" 규칙을 만들어 임시 폴더에 빌드한다. 적용 불가 0, 바뀐 유닛 수, 건너뛴 이유별 수를 찍는다.
- 화면: 한 번 실행으로 규칙 창·미리 보기·수정 목록 묶음을 찍는다(`--scenario`에 규칙 명령을 더한다).

## 위험과 미확인

- 대상이 넓으면 '이 유닛만' 사본이 유닛마다 생겨 출력 파일이 많아진다(E18에서 1,378개). 미리 보기에 만들어질 사본 수를 보인다.
- 펼친 키가 매크로 정의 안에서 온 값이면 '이 유닛만'이 안 되고(매크로 본문), 대상 밖 유닛도 그 매크로를 쓰면 `auto`는 건너뛴다. 그런 값이 많으면 규칙의 효과가 작다. 미리 보기의 건너뛴 이유로 드러난다.
- 키의 뜻은 주석 등급(확인·추정·미확인)이 정한다. 미확인 키에 규칙을 걸면 창이 경고한다(막지는 않는다).

## 빌더에게 맡기는 것

- 규칙 `id`의 꼴, 프로젝트 파일에서 `rules`의 정확한 필드 이름.
- 미리 보기 계산의 캐시(유닛을 펼치는 비용. 탱크 전부면 수백 대).
- 규칙 창의 배치.

## 구현 결과 (2026-10-17)

- 코어 `BulkRules.cs`·`EditorSession.Rules.cs`, 명령줄 `rule`, 앱 `RuleDialog`·줄 메뉴·수정 목록 규칙 묶음과 단추. 계획: `docs/superpowers/plans/2026-10-17-f1-bulk-rules.md`.
- 프로젝트 파일: `rules`(규칙 목록)와 수정의 `rule`(규칙 id, 8자). 규칙이 없으면 두 필드를 쓰지 않아 예전 파일과 같다.
- 빌더 몫으로 정한 것: 규칙 id는 GUID 앞 8자. 미리 보기 캐시는 두지 않았다(앱 시나리오에서 경전차 161대 미리 보기 두 번과 넣기까지, 실행 전체가 26초). 규칙 창은 위에 칸, 아래에 바뀜·건너뜀 목록. 꺼진 규칙은 수정이 없어 목록에 안 보이므로 수정 목록 아래 "일괄 규칙" 칸에서 고른다(설계의 "묶음 머리 단추" 대신).
- 미리 보기는 값이 그대로인 자리와 읽지 못한 유닛도 건너뜀으로 센다. 그래서 대상 유닛은 모두 "바뀜"이나 "건너뜀(이유)" 가운데 하나다.
- 실제 파일 검사(`-- real`, 모든 탱크 `**/locomotion/maxspeed` ×1.1): 대상 782, 바뀐 유닛 781, 바뀐 값 782, 수정 761, 건너뜀 1(값이 0이라 그대로), 적용 불가 0, 파일 오류 0.
- 화면: 한 번 실행 시나리오(`rule`·`rulerow`·`rulepreview`·`ruleok`)로 창·미리 보기·수정 목록 묶음을 찍어 보고, 앞 규칙을 id 대신 이름으로 보이게, 키를 `**/꼬리`로 줄이는 단추, 규칙 칸 배치를 고쳤다.
